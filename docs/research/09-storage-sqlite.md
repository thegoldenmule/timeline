# Storage design research: event-sourced SQLite project files on macOS 26

Verified 2026-09-08. Facts marked **[local]** were measured on this machine (macOS 26.3 build 25D125, Apple M4 Max). Facts marked *[memory]* could not be re-verified online (web-search budget exhausted; direct fetches used instead) and should be treated as background, not citation.

## 1. Swift SQLite libraries

**GRDB.swift** — v7.11.1 (2026-06-18), MIT, 8.6k stars, last push 2026-08-08 (GitHub API). Requirements: Swift 6.1+/Xcode 16.3+, macOS 10.15+, SQLite 3.20+ ([README](https://github.com/groue/GRDB.swift)). `Package.swift` declares `swiftLanguageModes: [.v6]`, i.e. the library itself compiles in Swift 6 strict-concurrency mode ([Package.swift](https://raw.githubusercontent.com/groue/GRDB.swift/master/Package.swift)). It links the **system** `libsqlite3` by default (`import SQLite3`); SQLCipher or a custom SQLite build are opt-in ([Custom SQLite builds](https://github.com/groue/GRDB.swift/blob/master/Documentation/CustomSQLiteBuilds.md)). Has `DatabaseMigrator` (incl. merged migrations, 7.8+), `ValueObservation` (drives SwiftUI/Combine/async sequences), `DatabasePool` (WAL, one writer + concurrent readers), FTS5 record support, `JSONColumn` with `->`/`->>` and expression indexes; upsert and `RETURNING` require SQLite 3.35+ ([JSON doc](https://raw.githubusercontent.com/groue/GRDB.swift/master/GRDB/Documentation.docc/JSON.md), [README upsert note](https://github.com/groue/GRDB.swift#upsert)). GRDB recommends storing JSON as TEXT because JSON functions error on non-JSONB blobs.

**SQLiteData (Point-Free)** — 1.12.0 (2026-08-31), MIT, 1.9k stars, pushed 2026-09-08. Built on GRDB + [swift-structured-queries](https://github.com/pointfreeco/swift-structured-queries) (0.39.2, "truly type-safe SQL", still 0.x). Adds `@FetchAll`/`@FetchOne` property wrappers with SwiftUI/`@Observable` observation, CloudKit sync and sharing, and faster decoding than GRDB Codable ([README](https://github.com/pointfreeco/sqlite-data)). *[memory]* It was renamed from SharingGRDB in 2025. Good ergonomics, but it drags in a fast-moving 0.x query DSL and CloudKit machinery you do not need.

**SQLite.swift** — 0.16.0 (2026-03-08), MIT, 10.2k stars; `swift-tools-version 6.1` but `swiftLanguageModes: [.v5]` (not Swift 6 mode), 134 open issues ([repo](https://github.com/stephencelis/SQLite.swift)). Maintained but slow; no observation layer.

**Lighter** — 1.4.8 (2024-10-26), MIT, 517 stars, pushed 2026-01. Generates Swift from a SQL schema at build time; no migrations or observation ([repo](https://github.com/Lighter-swift/Lighter)).

**Blackbird** — tag 0.5, MIT, ~1k stars, pushed 2026-08, Swift 6 mode, macOS 12+; self-described beta with automatic schema migration ([repo](https://github.com/marcoarment/Blackbird)). Auto-migration is the wrong model for an event store.

**Raw sqlite3 C API** — always available; you lose migrations/observation/Sendable-safe connection management and gain nothing you cannot get through GRDB's `db.sqliteConnection` escape hatch.

**Recommendation:** GRDB 7.x, system SQLite, Swift 6 mode. Use `DatabasePool` for the project DB, `DatabaseMigrator` for schema, `ValueObservation` for SwiftUI projections. Do not adopt SQLiteData/StructuredQueries yet (0.x DSL churn, CloudKit focus); revisit once StructuredQueries is 1.0.

## 2. SQLite features and the macOS 26 build

**[local]** `/usr/lib/libsqlite3.dylib` on macOS 26.3 reports `sqlite_version() = 3.51.0` (Apple build string "2025-06-12 … aapl"). Verified working: `jsonb()`/`jsonb_extract` (JSONB), STRICT tables, generated columns indexed on `jsonb_extract`, `RETURNING`, `ON CONFLICT … DO UPDATE`, FTS5, `VACUUM INTO`, `PRAGMA optimize`, `PRAGMA user_version`. Compile options of note: `ENABLE_FTS5`, `ENABLE_RTREE`, `ENABLE_SESSION`, `ENABLE_PREUPDATE_HOOK`, `ENABLE_SNAPSHOT`, `OMIT_LOAD_EXTENSION` (no runtime extensions), `DEFAULT_WAL_SYNCHRONOUS=1` (Apple defaults WAL connections to `synchronous=NORMAL`), `DEFAULT_CKPTFULLFSYNC` (`checkpoint_fullfsync=1`, F_FULLFSYNC at checkpoints), `DEFAULT_JOURNAL_SIZE_LIMIT=32768`, `auto_vacuum=0`, `THREADSAFE=2`.

Upstream timeline ([changes.html](https://sqlite.org/changes.html)): JSONB 3.45.0 (2024-01-15); `PRAGMA optimize` auto analysis limits 3.46.0; `sqlite3_rsync` 3.47.0; `sqlite3_setlk_timeout` 3.50.0; `jsonb_each/jsonb_tree` 3.51.0 (2025-11-04); **3.51.3 (2026-03-13) fixed a "WAL-reset database corruption bug"** — the macOS 26 build predates this fix, so keep an eye on Apple's point releases or ship a custom SQLite if it matters.

Feature notes:
- **JSON/JSONB** ([json1](https://www.sqlite.org/json1.html), [jsonb](https://sqlite.org/jsonb.html)): JSONB is 5–10% smaller and parses in under half the CPU cycles, but "is not intended as an external format" and remains O(N) lookup. Text-JSON stored as BLOB raises errors. Decision: store payload as TEXT (portable, diffable in `sqlite3` CLI) or JSONB BLOB (faster projections); either way only read it through JSON functions or your Codable decoder.
- **Generated columns** ([gencol](https://sqlite.org/gencol.html)): 3.31+, VIRTUAL or STORED, both indexable; STORED cannot be added via `ALTER TABLE`; **[local]** in STRICT tables they must carry a type (`a INTEGER AS (jsonb_extract(payload,'$.a'))`). Use VIRTUAL + index for hot payload fields (e.g. `clip_id`).
- **STRICT** ([stricttables](https://sqlite.org/stricttables.html)): 3.37+, types INT/INTEGER/REAL/TEXT/BLOB/ANY; files with STRICT tables are unreadable by SQLite < 3.37 (irrelevant on macOS 12+).
- **FTS5** ([fts5](https://www.sqlite.org/fts5.html)): use an external-content table (`content='transcript_segments', content_rowid='id'`) kept in sync by triggers, `unicode61` or `porter` tokenizer, `bm25()` ranking, `highlight()/snippet()`; `trigram` for substring search. Rebuild with `INSERT INTO ft(ft) VALUES('rebuild')` since it is a derived index.
- **RETURNING** ([lang_returning](https://www.sqlite.org/lang_returning.html)) 3.35+; output order not guaranteed. **Upsert** ([lang_upsert](https://www.sqlite.org/lang_upsert.html)) 3.24+, multi-clause 3.35+; add `WHERE true` when the source is a SELECT.
- **WAL** ([wal.html](https://sqlite.org/wal.html)): one writer, many readers; auto-checkpoint at 1000 pages (~4 MB); long-lived readers cause checkpoint starvation and unbounded `-wal` growth; `-wal`/`-shm` must travel with the file; not for network filesystems. `synchronous=NORMAL` in WAL keeps consistency but may lose the last transactions on power loss — acceptable for an editor whose events are replayable from user intent, but pair it with periodic `PRAGMA wal_checkpoint(TRUNCATE)` on idle and on close.
- **Pragmas** ([pragma.html](https://sqlite.org/pragma.html)): `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON` (off by default), `busy_timeout=5000`, `journal_size_limit` (Apple's default 32 KB already truncates the WAL after checkpoints), `user_version` for your schema number (32-bit header field ignored by SQLite), `PRAGMA optimize` on close and ~daily for long-lived connections (3.46+ needs no analysis_limit tuning).
- **Safe copies** ([backup.html](https://www.sqlite.org/backup.html), [lang_vacuum](https://sqlite.org/lang_vacuum.html), [howtocorrupt](https://sqlite.org/howtocorrupt.html)): never `FileManager.copyItem` a live DB (partial transactions, orphaned WAL). Use `VACUUM INTO 'path'` for compact snapshots/Save-As and the incremental backup API for background backups of a hot DB (external writers restart it). `sqlite3_rsync` (3.47+) exists but is not in the OS build's CLI story.
- **Append-only file size**: without deletes there is no freelist, so the file grows monotonically by page; `auto_vacuum` is off by default (**[local]**) and unnecessary. Reclaim only via `VACUUM INTO` when compacting a history you have snapshotted.

**Recommendation:** Target the system 3.51.0 (JSONB, STRICT, RETURNING, FTS5 all present). Schema: STRICT tables, TEXT or JSONB payloads with VIRTUAL generated columns for indexed fields, FTS5 external-content table for transcripts, `user_version` driven by GRDB migrations, WAL + NORMAL + foreign_keys + busy_timeout, `wal_checkpoint(TRUNCATE)` + `optimize` on close, `VACUUM INTO` for copies.

## 3. Event sourcing on SQLite: prior art

- **Python `eventsourcing` SQLite recorder** ([docs](https://eventsourcing.readthedocs.io/en/stable/topics/persistence.html), [sqlite.py](https://raw.githubusercontent.com/pyeventsourcing/eventsourcing/main/eventsourcing/sqlite.py)): `stored_events(originator_id, originator_version, topic, state)` with a UNIQUE/PK on `(originator_id, originator_version)`, plus an autoincrement `notification_id` as the global sequence; a `tracking(application_name, notification_id)` table with a composite PK gives exactly-once projection checkpoints by committing the checkpoint in the same transaction as the projection write; snapshots live in a separate table so they never collide with the version constraint; WAL is enabled automatically.
- **Rails Event Store** ([expected version](https://railseventstore.org/docs/core-concepts/expected-version/)): `expected_version: integer` = optimistic lock raising `WrongExpectedEventVersion`; `:any` = no ordering; `:auto` = read-then-write requiring external locking; never mix modes on one stream. Schema splits `events` (global position, event_id) from `events_in_streams` (stream, position).
- **Marten** ([appending](https://martendb.io/events/appending.html), [versioning](https://martendb.io/events/versioning.html)): stream version vs. global sequence; prefer a `FetchForWriting`-style API that loads state and stamps the expected version for you; schema evolution = event-type-name mapping + upcasters (typed or raw-JSON, registered per old type), never rewriting history.
- **Undo/redo**: Figma treats undo as applying inverse operations and lets undo rewrite the redo stack so "undo, copy, redo" leaves the document unchanged and never clobbers collaborators ([Figma blog](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). Yjs `UndoManager` groups edits within `captureTimeout` (500 ms) into one undo unit, exposes `stopCapturing()` to force a boundary, and undoes only `trackedOrigins` ([Yjs docs](https://docs.yjs.dev/api/undo-manager)). Both are compensating-event models: the undo itself is a new, forward event. *[memory]* Photoshop-style linear history is snapshot-based and single-user; Linear/Descript-style apps use per-transaction inverse deltas.
- **Idempotency**: Rails Event Store enforces a unique `event_id`; *[memory]* EventStoreDB deduplicates appends by event UUID only within a recent window and per stream. For your LLM tool-call retry case do it explicitly in SQL.

**Recommendation (schema sketch):**
```sql
CREATE TABLE events (
  seq        INTEGER PRIMARY KEY,           -- global order (rowid)
  stream_id  TEXT    NOT NULL,              -- e.g. 'timeline:<uuid>'
  version    INTEGER NOT NULL,              -- per-stream, 1..n
  type       TEXT    NOT NULL,              -- 'ClipTrimmed'
  schema_v   INTEGER NOT NULL DEFAULT 1,    -- payload version for upcasting
  payload    TEXT    NOT NULL,              -- JSON (or BLOB jsonb)
  command_id TEXT    NOT NULL,              -- idempotency key from the caller
  tx_group   TEXT    NOT NULL,              -- undo unit (one user gesture / one tool call)
  actor      TEXT    NOT NULL,              -- 'user' | 'agent:<run>'
  created_at INTEGER NOT NULL,
  UNIQUE(stream_id, version),
  UNIQUE(command_id)
) STRICT;
CREATE TABLE snapshots(stream_id TEXT, version INTEGER, state BLOB, PRIMARY KEY(stream_id, version)) STRICT;
CREATE TABLE projections(name TEXT PRIMARY KEY, last_seq INTEGER NOT NULL) STRICT;
```
Append = one transaction: check `command_id` (return the original result on conflict, so a retried tool call is a no-op), insert with expected `version`, let `UNIQUE(stream_id, version)` raise on races, update projections and `projections.last_seq` in the same transaction. Snapshot every N events or on close; keep snapshots outside `events`. Upcast on read by `(type, schema_v)`; never mutate stored payloads. Undo = append inverse events tagged `undoes_tx_group`; redo re-appends the originals; the redo stack is cleared when a new tx_group lands. Agent actions get their own tx_group so the user can undo an entire tool call at once.

## 4. Document package conventions on macOS

- A directory is a package when its extension's UTI conforms to `com.apple.package` (declare via `UTExportedTypeDeclarations`, and `LSTypeIsPackage` in `CFBundleDocumentTypes`); Finder shows it as one file; `NSDocument` reads/writes it through `FileWrapper` (`read(from:ofType:)` / `fileWrapper(ofType:)`) ([Document Packages](https://developer.apple.com/library/archive/documentation/CoreFoundation/Conceptual/CFBundles/DocumentPackages/DocumentPackages.html)). iCloud uploads only the changed members of a package ([iCloud Design Guide](https://developer.apple.com/library/archive/documentation/General/Conceptual/iCloudDesignGuide/Chapters/DesigningForDocumentsIniCloud.html)) — which is exactly what makes a live SQLite file inside a synced package dangerous: the syncer may copy `project.sqlite` mid-transaction or without its `-wal`, the precise corruption modes SQLite documents ([howtocorrupt](https://sqlite.org/howtocorrupt.html)).
- Apple's own precedent: Core Data switched to WAL in 10.9 and QA1809 tells developers to copy the store, `-wal` and `-shm` together "as a single document package", use `migratePersistentStore`, or force `journal_mode=DELETE` via `NSSQLitePragmasOption` ([QA1809](https://developer.apple.com/library/archive/qa/qa1809/_index.html)). Core Data's deprecated iCloud integration synced transaction logs, never the SQLite file ([archived guide](https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/UsingCoreDataWithiCloudPG/UsingSQLiteStoragewithiCloud/UsingSQLiteStoragewithiCloud.html)).
- Final Cut Pro uses a library package with independently relocatable Media, Motion Content, Cache and Backups; backups default to `~/Movies/Final Cut Backups` outside the library ([FCP guide](https://support.apple.com/guide/final-cut-pro/set-storage-locations-ver7db6ffe77/mac)). *[memory]* The library contains a SQLite/CoreData-derived `CurrentVersion.flexolibrary`; Logic uses a `.logicx` package with optional embedded assets; DaVinci Resolve keeps projects in a PostgreSQL/SQLite database outside any document; Descript projects are cloud-resident.

**Recommendation:** Yes to a `.tlproj` directory package: `project.sqlite` (+ `-wal`/`-shm`), `manifest.json` (format version, app version, project id, relative media roots), `thumbs/` optional. Do **not** use `NSDocument`'s whole-package rewrite path for the DB — open SQLite in place and use `FileWrapper` only for the sidecar files, or subclass `NSDocument` with autosave disabled for the DB member (`NSPersistentDocument` is the model). Keep derived caches (proxies, waveforms) in `~/Library/Caches/<bundle-id>/cas/<sha256>` so the package stays small and sync-tolerable. Detect cloud-synced locations (`URLResourceKey.isUbiquitousItemKey`, path under `~/Library/Mobile Documents`, Dropbox/Drive markers) and warn: "Store projects in a local folder; sync services can corrupt an open project." If the user insists, switch that project to `journal_mode=DELETE` + `synchronous=FULL` so there is only one file to sync, and checkpoint/TRUNCATE aggressively. Refuse network volumes for WAL.

## 5. IDs and hashing

- **UUIDv7 in Foundation**: swift-foundation proposal SF-0041 "UUID versions" (review 2026-05-20…27, PR #1836) adds `UUID.version7(at:offset:)`, `UUID.version4()`, `UUID.min/max` with RFC 9562 method-3 sub-millisecond bits ([proposal](https://raw.githubusercontent.com/swiftlang/swift-foundation/main/Proposals/0041-uuid-versions.md)). It is not in the macOS 26 SDK; plan on a package until it ships: [mhayes853/swift-uuidv7](https://github.com/mhayes853/swift-uuidv7) (RFC 9562, GRDB/StructuredQueries integrations, active 2026-08), [block/uuidv7](https://github.com/block/uuidv7) (minimal), or ULID via [yaslab/ULID.swift](https://github.com/yaslab/ULID.swift) (134 stars, active). Prefer UUIDv7: it is a real `UUID` (16-byte BLOB in SQLite, `Codable`, bridges to `NSUUID`) and sorts by creation time, which keeps your `stream_id`/`command_id` indexes append-friendly.
- **Hashing**: **[local]** CryptoKit `SHA256` over a 1 GiB file, 8 MiB chunks, one core on M4 Max: **~2.26 GB/s** (openssl 3: ~2.5 GB/s; perl `shasum` ~0.53 GB/s). Apple Silicon has SHA-256 hardware, so a single core already exceeds most SSD read speeds for ProRes/H.264 sources. BLAKE3 claims order-of-magnitude wins mainly through multithreading ([BLAKE3](https://github.com/BLAKE3-team/BLAKE3)); Swift bindings are small hobby projects ([nixberg/blake3-swift](https://github.com/nixberg/blake3-swift), [JoshBashed/blake3-swift](https://github.com/JoshBashed/blake3-swift), [Argsment/BLAKE3](https://github.com/Argsment/BLAKE3)). Not worth the dependency risk.
- **Cheap file identity**: `URLResourceKey.fileIdentifierKey` (inode, macOS 13.3+; Apple says do not persist it), `fileResourceIdentifierKey`, `fileContentIdentifierKey` (APFS content-stream id, shared by clones), `fileSizeKey`, `contentModificationDateKey` ([fileIdentifierKey](https://developer.apple.com/documentation/foundation/urlresourcekey/fileidentifierkey)). **[local]** all three identifier keys return values on APFS.

**Recommendation:** UUIDv7 (package now, Foundation later) stored as 16-byte BLOB. Content address = SHA-256 via CryptoKit, streamed in 4–8 MiB chunks off the main actor; cache `(volumeUUID, fileContentIdentifier or inode, size, mtime) -> sha256` and only rehash when the tuple changes; treat the tuple as a hint, never as identity across volumes. Optionally hash the first+last 64 MiB + size for an instant "probably same" pre-check on multi-GB files.

## 6. Time representation

- **OTIO** `RationalTime` is `{value: double, rate: double}` with `rescaled_to`, `to_frames`, `is_smpte_timecode_rate`/`nearest_smpte_timecode_rate` (23.976, 24, 25, 29.97, 30, 50, 59.94, 60), and `TimeRange(start_time, duration)` with exclusive/inclusive end helpers ([opentime API](https://opentimelineio.readthedocs.io/en/latest/api/python/opentimelineio.opentime.html), [rationalTime.h](https://raw.githubusercontent.com/AcademySoftwareFoundation/OpenTimelineIO/main/src/opentime/rationalTime.h)). Doubles for both fields means 29.97 is stored as an inexact float; OTIO papers over it with epsilon comparisons.
- **CMTime** is `{value: Int64, timescale: Int32, flags, epoch}`; conversions go through `convertScale(_:method:)` with explicit rounding and set `hasBeenRounded` ([CMTime](https://developer.apple.com/documentation/coremedia/cmtime)). 600 is Apple's historical common denominator (divides 24/25/30/60 but not 23.976); 24000 handles 23.976/24/30/60; 30000 for 29.97; 48000 for audio.
- **FCPXML** 1.10 writes every time as rational seconds with an `s` suffix (`"0s"`, `"1000/30000s"`), formats carry `frameDuration`, and timelines a `tcFormat` NDF/DF; `.fcpxmld` bundles keep the XML with referenced files ([Creating FCPXML](https://developer.apple.com/documentation/professional-video-applications/creating-fcpxml-documents), [FCPXML reference](https://developer.apple.com/documentation/professional-video-applications/fcpxml-reference)).

**Recommendation:** Store `{value: Int64, timescale: Int32}` pairs (exactly `CMTime` minus flags) in the events, as two INTEGER columns or a JSON `[value, timescale]`. A single project timescale forces lossy rounding the moment 23.976 video meets 48 kHz audio or a 29.97 clip is dropped into a 25 fps sequence; per-value pairs stay exact and round-trip to CMTime, OTIO and FCPXML without loss. Give each *sequence* a canonical frame duration (`1001/24000` etc.) and snap edit points to it at command time, so projections can compare with integer arithmetic; when you must compare mixed-rate values, cross-multiply in Int128/Double, never rescale and store. Persist durations, not end times, matching OTIO/FCPXML semantics.
